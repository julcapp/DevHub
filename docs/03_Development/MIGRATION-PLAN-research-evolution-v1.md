# Migration Plan: Research & Evolution Core v1

Статус: Approved for implementation planning

## Этап 0. Подготовка

- добавить PostgreSQL как отдельный инфраструктурный сервис;
- зафиксировать версию PostgreSQL;
- выбрать Alembic как механизм миграций;
- не переносить текущие локальные настройки DevHub в БД на первом шаге;
- сохранить совместимость текущего desktop-приложения v0.4 Alpha.

## Этап 1. Core schema

Создать:

- `core.engineering_objects`;
- `core.object_relations`;
- `core.audit_events`;
- генератор EO-ID;
- базовые справочники типов объектов и отношений.

Критерий готовности: можно создать, прочитать, архивировать EO и связать два объекта.

## Этап 2. Projects and repositories

Создать:

- `projects.projects`;
- `projects.repositories`;
- импорт текущего реестра локальных репозиториев;
- сопоставление `.devhub/project.json` с Project EO.

Критерий готовности: существующий Git Manager продолжает работать, а данные параллельно представлены как Engineering Objects.

## Этап 3. GitHub Stars

Создать:

- импорт starred repositories через GitHub API;
- дедупликацию по GitHub repository ID;
- карточку Star EO;
- раздельные поля GitHub metadata и пользовательских заметок;
- повторную синхронизацию без потери решений пользователя.

Критерий готовности: все звёздочки импортируются повторяемо и не создают дублей.

## Этап 4. AI Analysis

Создать:

- очередь анализа;
- `ai.analysis_versions`;
- анализ README, лицензии, активности, стека и рисков;
- ручное подтверждение решения;
- запрет AI автоматически создавать fork или коммерческий проект.

Критерий готовности: анализ версионируется, а пользовательское решение хранится отдельно.

## Этап 5. Research and Ideas

Создать:

- исследования;
- идеи;
- связи Idea ↔ Research ↔ Star ↔ Technology;
- статусы и следующие действия;
- журнал решений.

## Этап 6. Derivative Project Wizard

Реализовать saga:

1. проверить лицензию;
2. получить подтверждение пользователя;
3. создать GitHub fork или новый репозиторий;
4. клонировать локально;
5. создать ветку разработки;
6. создать Project и Repository EO;
7. создать EvolutionNode;
8. сохранить upstream и commit происхождения;
9. сформировать паспорт `.devhub/project.json`;
10. записать аудит.

При сбое внешней операции saga должна сохранять состояние и предлагать безопасное повторение, а не создавать дубликаты.

## Этап 7. Evolution Tree

- визуализировать происхождение;
- показывать upstream, fork, производные проекты и поколения;
- поддержать снимок лицензии;
- показывать расхождения с upstream;
- подготовить сценарий обновления производного проекта.

## Политика совместимости

До завершения этапа 2 PostgreSQL-функции включаются feature flag. Текущий JSON и локальный реестр остаются источником для старого UI. После стабилизации БД вводится dual-write, затем чтение переводится на PostgreSQL.

## Политика отката

- каждая миграция имеет downgrade там, где это безопасно;
- данные происхождения и аудита не удаляются автоматическим downgrade;
- destructive migrations требуют резервной копии и отдельного ADR;
- GitHub fork и локальный clone не откатываются SQL-миграцией, их состояние фиксируется saga.

## Минимальный тестовый набор

- уникальность EO-ID;
- запрет дублей GitHub Stars;
- сохранение user_notes после повторной синхронизации;
- архивирование объекта без потери связей;
- создание цепочки Star → Research → Fork → Project;
- отказ создания производного проекта при несовместимой лицензии;
- повтор saga после частичного сбоя;
- полнота audit trail.
