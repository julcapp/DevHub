# DevHub — Architecture Overview

**Документ:** Architecture Overview  
**Версия:** 1.0  
**Статус:** Draft for Review  
**Проект:** DevHub  
**Репозиторий:** `julcapp/DevHub`  

---

## 1. Назначение документа

Этот документ определяет целевую архитектуру платформы DevHub: её границы, ключевые подсистемы, правила взаимодействия, жизненный цикл приложения и механизм расширения.

Документ является исходной точкой для последующих спецификаций Platform Core, DDS, DHS, модулей, публичных контрактов и записей архитектурных решений.

---

## 2. Архитектурная цель

DevHub развивается как настольная инженерная платформа, объединяющая проекты, Git и GitHub, документацию, архитектурные сведения, аналитику и интеллектуальные функции в одном рабочем пространстве.

Главная архитектурная цель:

> Новый функциональный модуль должен подключаться к DevHub без изменения ядра платформы и без прямой зависимости от внутренних реализаций других модулей.

---

## 3. Область ответственности платформы

DevHub отвечает за:

- регистрацию и управление инженерными проектами;
- работу с локальными Git-репозиториями;
- интеграцию с GitHub;
- хранение и чтение метаданных DHMS;
- навигацию между рабочими пространствами и модулями;
- единые настройки, темы, события, уведомления и журналирование;
- подключение модулей и предоставляемых ими возможностей;
- формирование инженерного контекста для DevAdvisor;
- контроль состояния проекта, документации и жизненного цикла.

DevHub не должен:

- хранить бизнес-логику пользовательских проектов внутри Platform Core;
- связывать модули через прямой импорт их внутренних классов;
- содержать секреты и учётные данные в исходном коде;
- смешивать UI, инфраструктуру и доменную логику в одном слое.

---

## 4. Архитектурные принципы

### 4.1. Модульность

Каждая функциональная область оформляется как отдельный модуль с определённой ответственностью, публичными контрактами и зависимостями.

### 4.2. Низкая связанность

Модули взаимодействуют через события, сервисные интерфейсы и capabilities. Прямой доступ к внутренним объектам другого модуля запрещён.

### 4.3. Высокая связность внутри модуля

В одном модуле размещается логика только одной предметной области.

### 4.4. Зависимость от абстракций

Потребитель использует контракт или capability, а не конкретную реализацию.

### 4.5. Конфигурация вместо жёсткого кодирования

Изменяемые параметры, пути, темы, интервалы, ограничения и флаги функций задаются конфигурацией или design tokens.

### 4.6. Наблюдаемость

Ключевые операции должны формировать структурированные записи журнала и диагностические события.

### 4.7. Безопасные значения по умолчанию

Опасные операции требуют явного подтверждения. Отсутствие конфигурации не должно приводить к разрушительным действиям.

### 4.8. Документация как часть продукта

Изменение архитектуры или публичного контракта считается незавершённым без обновления документации.

## 6. Основные подсистемы

### 6.1. Application Core

Отвечает за:

- запуск и завершение приложения;
- инициализацию Platform Services;
- загрузку конфигурации;
- обнаружение и активацию модулей;
- обработку критических ошибок;
- последовательное освобождение ресурсов.

Application Core не содержит бизнес-логики отдельных модулей.

### 6.2. Configuration Manager

Обеспечивает:

- загрузку настроек из файлов и переменных окружения;
- проверку схемы конфигурации;
- значения по умолчанию;
- разделение общих, пользовательских и проектных настроек;
- уведомление об изменении настроек.

Приоритет источников:

```text
значения по умолчанию
    < системная конфигурация
    < пользовательская конфигурация
    < конфигурация рабочего пространства
    < переменные окружения
    < параметры запуска
```

### 6.3. Service Registry

Регистрирует сервисы платформы и предоставляет их потребителям через публичные интерфейсы.

Требования:

- уникальный идентификатор сервиса;
- явный жизненный цикл;
- запрет скрытых глобальных singleton-объектов;
- возможность подмены реализации в тестах;
- диагностика отсутствующих и циклических зависимостей.

### 6.4. Event Bus

Обеспечивает слабосвязанное взаимодействие между подсистемами.

Типы событий:

- доменные события;
- события приложения;
- события интерфейса;
- диагностические события.

Примеры:

```text
ProjectOpened
ProjectClosed
RepositoryStatusChanged
ConfigurationChanged
ThemeChanged
ModuleActivated
OperationFailed
```

Событие должно быть неизменяемым объектом с типом, временем, источником, correlation ID и полезной нагрузкой.

### 6.5. Navigation Manager

Отвечает за:

- реестр маршрутов;
- переходы между экранами;
- историю навигации;
- возврат на главную;
- синхронизацию маршрута с боковой панелью;
- проверку доступности маршрута;
- восстановление последнего безопасного состояния.

Модуль регистрирует маршрут, но не изменяет код Navigation Manager.

### 6.6. Theme Manager и Token System

Обеспечивают применение DevHub Design System.

Все визуальные значения должны поступать из design tokens:

- цвета;
- типографика;
- отступы;
- размеры;
- радиусы;
- тени;
- анимации.

Компонент не должен содержать произвольные визуальные значения, если соответствующий токен уже существует.

### 6.7. Module Manager

Отвечает за:

- обнаружение модулей;
- проверку манифеста;
- разрешение зависимостей;
- регистрацию сервисов, маршрутов и capabilities;
- активацию и деактивацию;
- изоляцию ошибки одного модуля от остальных.

### 6.8. Workspace Engine

Рабочее пространство представляет один инженерный проект или согласованную группу ресурсов.

Минимальная модель рабочего пространства:

```text
Workspace
├── identity
├── project metadata (DHMS)
├── local repository
├── remote providers
├── documents
├── tasks and activity
├── module state
└── AI context
```

Workspace Engine не реализует Git, GitHub или AI самостоятельно. Он координирует capabilities соответствующих модулей.

### 6.9. Logging и Diagnostics

Система журналирования должна поддерживать:

- уровни DEBUG, INFO, WARNING, ERROR, CRITICAL;
- структурированные поля;
- correlation ID операции;
- источник и модуль;
- безопасную фильтрацию секретов;
- вывод в файл и интерфейсный журнал;
- диагностический пакет для анализа ошибок.

## 7. Модель модуля

Каждый модуль должен иметь манифест.

Пример:

```yaml
id: devhub.git
name: Git
version: 1.0.0
api_version: 1
entry_point: modules.git.module:GitModule
requires:
  - devhub.core>=1.0
capabilities:
  - RepositoryProvider
  - BranchProvider
  - DiffProvider
routes:
  - git.repositories
```

Обязательные элементы модуля:

```text
module/
├── manifest
├── contracts
├── domain
├── application
├── infrastructure
├── ui
├── tests
└── README
```

Модуль обязан объявлять:

- назначение;
- владельца;
- публичные контракты;
- capabilities;
- зависимости;
- маршруты;
- настройки;
- события;
- требования к данным;
- статус зрелости.

## 8. Capability Model

Capability — публично объявленная возможность, которую предоставляет один модуль и использует другой.

Примеры:

```text
RepositoryProvider
BranchProvider
RemoteRepositoryProvider
DocumentationProvider
ArchitectureProvider
ChatProvider
CodeReviewProvider
NotificationProvider
```

Правила:

1. Capability описывается интерфейсом и версией контракта.
2. Реализаций одной capability может быть несколько.
3. Выбор реализации выполняет Service Registry или пользовательская конфигурация.
4. Потребитель не импортирует внутренние классы поставщика.
5. Несовместимое изменение контракта требует новой major-версии.

## 9. Потоки взаимодействия

### 9.1. Открытие рабочего пространства

```text
Пользователь
  → Navigation Manager
  → Workspace Engine
  → Project Metadata Provider
  → RepositoryProvider
  → Event Bus: ProjectOpened
  → заинтересованные модули
  → обновление UI
```

### 9.2. Синхронизация Git

```text
UI-команда
  → Application Use Case
  → RepositoryProvider
  → Git Infrastructure Adapter
  → локальный Git
  → RepositoryStatusChanged
  → Workspace Engine / UI / Logging
```

### 9.3. Анализ DevAdvisor

```text
Пользователь или планировщик
  → Analysis Use Case
  → Workspace Context
  → DocumentationProvider
  → RepositoryProvider
  → ArchitectureProvider
  → правила и AI-провайдеры
  → AnalysisCompleted
  → отчёт и рекомендации
```

## 10. Жизненный цикл приложения

```text
1. Bootstrap
2. Загрузка минимальной конфигурации
3. Инициализация Logging
4. Создание Service Registry
5. Создание Event Bus
6. Загрузка Theme Manager и DDS tokens
7. Обнаружение модулей
8. Проверка зависимостей и контрактов
9. Регистрация сервисов, routes и capabilities
10. Восстановление безопасного состояния сессии
11. Запуск главного окна
12. Рабочий цикл
13. Сохранение состояния
14. Деактивация модулей
15. Освобождение сервисов
16. Завершение Logging
```

Критическая ошибка отдельного необязательного модуля не должна препятствовать запуску ядра. Пользователь получает диагностическое сообщение и возможность запустить платформу в безопасном режиме.

## 12. Данные и хранение

На первом этапе используются файловые форматы:

- JSON — пользовательские настройки и DHMS;
- YAML — декларативные манифесты и сложные конфигурации;
- Markdown — документация и записи решений;
- локальные журналы — диагностические данные.

Требования:

- атомарная запись конфигурации;
- резервная копия перед миграцией схемы;
- явная версия формата;
- проверка схемы при чтении;
- отсутствие секретов в открытых проектных файлах.

При появлении задач, требующих индексации, полнотекстового поиска или связей между сущностями, допускается внедрение локальной базы данных через отдельный StorageProvider.

---

## 13. Безопасность

Минимальные требования:

- секреты хранятся вне репозитория;
- токены GitHub не выводятся в журнал;
- внешние команды формируются без небезопасной конкатенации строк;
- операции удаления, force push и перезаписи требуют подтверждения;
- модуль получает только необходимые разрешения;
- данные рабочего пространства изолируются по контексту;
- импортируемые конфигурации проходят валидацию;
- диагностические пакеты очищаются от секретов.

---

## 14. Обработка ошибок

Ошибки классифицируются:

```text
DomainError
ApplicationError
ConfigurationError
IntegrationError
ModuleError
ValidationError
SecurityError
UnexpectedError
```

Публичная ошибка должна содержать:

- понятное сообщение для пользователя;
- технический код;
- correlation ID;
- рекомендуемое действие;
- безопасные диагностические сведения.

UI не должен показывать необработанный traceback обычному пользователю.

## 15. Тестовая стратегия

### Unit Tests

Проверяют доменные правила, конфигурацию, события и сервисы без PySide6 и внешних систем.

### Contract Tests

Проверяют совместимость capabilities и публичных интерфейсов.

### Integration Tests

Проверяют взаимодействие с Git, файловой системой, GitHub adapters и хранилищем.

### UI Tests

Проверяют критические пользовательские сценарии и навигацию.

### Architecture Tests

Контролируют запрещённые зависимости и границы слоёв.

---

## 16. Производительность

Целевые требования первой версии:

- главное окно появляется без ожидания полного анализа всех проектов;
- длительные операции выполняются вне UI-потока;
- список проектов загружается инкрементально;
- повторные вычисления используют кэш с явной политикой инвалидирования;
- события высокой частоты агрегируются;
- модуль не должен блокировать запуск платформы без критической причины.

---

## 17. Совместимость и версионирование

Используется Semantic Versioning:

```text
MAJOR.MINOR.PATCH
```

Версионируются отдельно:

- платформа;
- модули;
- публичные контракты;
- DHMS;
- конфигурационные схемы;
- DDS tokens.

Платформа должна проверять `api_version` модуля до его активации.

## 18. Миграция от текущей архитектуры

Миграция выполняется малыми обратимыми этапами.

### Этап A — Инвентаризация

- зафиксировать текущие зависимости `app`;
- определить UI, доменную и инфраструктурную логику;
- добавить базовые архитектурные тесты.

### Этап B — Platform Services

- внедрить Configuration Manager;
- внедрить Logging;
- внедрить Event Bus;
- внедрить Service Registry.

### Этап C — Навигация и DDS

- вынести Navigation Manager;
- внедрить Token System и Theme Manager;
- заменить прямые стили DDS-компонентами.

### Этап D — Выделение доменов

- вынести модели Project, Repository и Workspace;
- отделить Git adapter от сценариев приложения;
- сформировать публичные контракты.

### Этап E — Модульная модель

- оформить Git как первый эталонный модуль;
- внедрить Module Manager;
- зарегистрировать capabilities;
- перевести остальные области по одной.

На каждом этапе существующий пользовательский сценарий должен оставаться работоспособным.

---

## 19. Критерии готовности архитектурного фундамента M1

Milestone M1 считается выполненным, когда:

- Platform Core запускает приложение и управляет жизненным циклом;
- Configuration Manager валидирует настройки;
- Event Bus и Service Registry покрыты тестами;
- Navigation Manager не зависит от конкретных страниц;
- Theme Manager использует DDS tokens;
- один функциональный модуль подключается через манифест;
- модуль предоставляет минимум одну capability;
- ошибка необязательного модуля не разрушает запуск;
- архитектурные границы контролируются тестами;
- документация соответствует фактической реализации.

---

## 20. Решения, требующие отдельных ADR/DDR

Следующие вопросы должны быть оформлены отдельными записями решений:

1. Синхронная или асинхронная реализация Event Bus.
2. Формат и схема манифеста модуля.
3. Механизм dependency injection и жизненные циклы сервисов.
4. Использование JSON, YAML или комбинированной конфигурации.
5. Модель фоновых задач в PySide6.
6. Границы Workspace Engine и Project Registry.
7. Хранение пользовательских секретов в Windows.
8. Политика совместимости API модулей.
9. Подход к архитектурным тестам.
10. Стратегия миграции существующего `app/engineering_intelligence_window.py`.
